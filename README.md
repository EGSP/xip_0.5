# xip 0.5

Минимальный агентский цикл поверх Yandex AI Studio через OpenAI-совместимый API.
Учебный стенд: показывает, как модель запрашивает вызовы инструментов и что происходит дальше.
Замысел и границы этапа — в [ПЛАН.md](ПЛАН.md).

## Терминология

| Слово | Что означает |
|---|---|
| **агентский цикл** | сам механизм: обращение к модели → исполнение инструментов → повтор |
| **прогон** | одно исполнение механизма: от сообщения пользователя до итогового ответа |
| **итерация** | один виток внутри прогона: обращение к модели плюс вызовы, которые оно затребовало |

## Запуск

```bash
cp .env.example .env
npm install
npm run check
npm start
```

`npm run check` проверяет настройку отдельно от интерфейса: получает IAM-токен и делает одно
обращение к модели. Запускать его первым, потому что сообщения об ошибках в нём не затираются
перерисовкой Ink.

## Команды

| Команда | Что делает |
|---|---|
| `npm start` | интерактивный интерфейс на Ink; требуется настоящий терминал |
| `npm run check` | проверка IAM-токена и доступности модели |
| `npm run once -- "<запрос>"` | один прогон без интерфейса, лента событий обычным выводом |
| `npm run typecheck` | проверка типов |
| `npm run trace:up` / `trace:down` | локальный приёмник трассировок (Jaeger) |

В интерфейсе: `Esc` — прервать текущий прогон, `/exit` — выход.

## Что видно в ленте

Одиночный вызов и пакет вызовов различаются начертанием. Модель может затребовать несколько
инструментов одним ответом; тогда они показываются деревом, а над ними стоит счётчик.

```
› брось кубик и получи случайное число от 1 до 100

  ⏺ 2 вызова одним ответом
  ├ roll_dice  count: 1, sides: 6
  │   ⎿ rolls: [1], sum: 1  ·  1 мс
  └ random_number  min: 1, max: 100
      ⎿ value: 42  ·  0 мс

  ⏺ write_note  text: "Кубик: 1"
    ⎿ written: "Кубик: 1", count: 1  ·  4 мс

  3 итерации  ·  3 вызова  ·  3251→404 ток.  ·  36.2 с
```

Отдельным цветом помечается текст, который модель прислала **в одном сообщении с вызовами**:

```
  ✎ текст модели вместе с вызовами: Бросаю кубик, чтобы получить случайное значение.
```

Итоговая строка прогона показывает расход токенов — по ней видно, во что обходится работа.

## Трассировка

Программа отправляет спаны по OpenTelemetry. Экспорт выключен, пока не задан адрес
приёмника: при пустом `OTEL_EXPORTER_OTLP_ENDPOINT` экспортёр не создаётся вовсе.

```bash
npm run trace:up
```

Поднимаются два приёмника; какой используется, определяет адрес в `.env`.

| Приёмник | Адрес в `.env` | Интерфейс | Для чего |
|---|---|---|---|
| **Phoenix** | `http://localhost:6006` | http://localhost:6006 | читать диалог: сообщения, вызовы инструментов, расход токенов |
| **Jaeger** | `http://localhost:4318` | http://localhost:16686 | смотреть время: водопад спанов, что заняло длительность прогона |

### Phoenix — чтение истории как диалога

В списке прогонов сразу видно запрос пользователя и итоговый ответ. При раскрытии прогона
вкладка **Input** показывает сообщения ролями `system` и `user` отдельными карточками,
вкладка **Output** — ответ ассистента, а вызов инструмента отображается карточкой
`Tool Call` с именем и аргументами. Вызовы инструментов — отдельные спаны с видом `tool`,
где виден и вход, и результат.

### Jaeger — чтение времени

```
invoke_agent                          26 040 мс
  ├ chat qwen3.6-35b-a3b/latest       24 598 мс
  ├ execute_tool roll_dice                 1 мс
  ├ execute_tool random_number             0 мс
  ├ chat qwen3.6-35b-a3b/latest          941 мс
  └ execute_tool write_note                3 мс
```

Из этого дерева видно то, чего не видно в ленте: почти всё время прогона — первое обращение
к модели, а инструменты не стоят ничего.

### Почему два набора атрибутов

Приёмники договорились по-разному. Соглашения OpenTelemetry для GenAI (`gen_ai.*`) понимает
Langfuse; соглашения OpenInference (`llm.*`, `openinference.span.kind`) понимает Phoenix.
Наборы не конфликтуют, поэтому выставляются оба сразу — это дешевле, чем привязка к одному
приёмнику.

Различие содержательное. `gen_ai.*` описывает обращение плоскими значениями: модель,
температура, число токенов. OpenInference дополнительно раскладывает диалог по сообщениям
(`llm.input_messages.0.message.role` и далее), и именно из этой раскладки Phoenix собирает
вид переписки. Без неё он показал бы такой же водопад, как Jaeger.

### Кодировка

Экспорт идёт в protobuf, а не в JSON. OTLP по HTTP допускает обе, но принимают их
по-разному: Jaeger понимает и ту и другую, Phoenix на JSON отвечает кодом 415. Protobuf
принимают все.

### Другие приёмники

| Приёмник | Адрес | Чем отличается |
|---|---|---|
| **Langfuse** | `http://localhost:3000/api/public/otel` | разбирает `gen_ai.*`, показывает переписку, стоимость по моделям, версии промптов и оценки качества; self-hosted, но тянет PostgreSQL, ClickHouse, Redis и S3-хранилище |
| **Grafana Tempo** | адрес коллектора | если трассировки уже собираются в Grafana; диалог не разбирает |
| **LangSmith** | облако LangChain | закрытый SaaS, данные уходят наружу |

Langfuse требует заголовка с ключами проекта: `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic <base64 pk:sk>`.

**О содержимом.** По умолчанию `OTEL_CAPTURE_CONTENT=true`, то есть в спаны попадают тексты
запросов и ответов модели: без них вид переписки не собирается. В рабочей системе значение
должно быть противоположным, иначе пользовательский ввод уходит в приёмник. В PIX этот флаг
(`EnableSensitiveData`) выключен по умолчанию именно поэтому.

## Конфигурация

Все переменные описаны в [.env.example](.env.example). Обязательна `YANDEX_MODEL` — без неё
программа не стартует и печатает перечень незаполненных значений.

Аутентификация — IAM-токен, двумя способами: готовый токен из `yc iam create-token`
(живёт около 12 часов) либо ключ сервисного аккаунта, из которого программа сама подписывает
JWT и обменивает его на IAM-токен, обновляя по мере истечения. Второй способ основной;
сервисному аккаунту нужна роль `ai.languageModels.user` на каталоге.

## Отступления от плана

1. **Прерывание прогона по `Esc`.** План этапа его исключал, но при интерфейсе на Ink это
   десять строк (`AbortController`, сигнал передаётся в запрос к модели), а без него
   долгий прогон нельзя остановить, не завершая программу.
2. **`run-once.ts`.** Понадобился, чтобы прогонять цикл там, где интерактивный ввод
   недоступен.
3. **Повторы при сетевых отказах.** В окружении разработки соединение нестабильно, и без
   повторов прогон обрывался на ровном месте. Повторяются только сетевые отказы; ответы с
   кодом состояния не повторяются, поскольку повтор их не устраняет.

## Что проверено на модели `qwen3.6-35b-a3b/latest`

**Цепочка зависимых вызовов.** «Брось два кубика, запиши сумму в заметки и покажи заметки» —
три вызова подряд (`roll_dice` → `write_note` → `read_notes`), верный итог.

**Восстановление после отказа инструмента.** При попытке записать четвёртую строку
`write_note` вернул ошибку с указанием вызвать `clear_notes`; модель прочитала текст, очистила
заметки и повторила все три записи. Это подтверждает правило из
`../Исследования архитектуры/Цикл агента/Как устроен цикл.md`: ошибка инструмента —
результат вызова, а не исключение, и её текст должен предписывать, что делать дальше.

**Пакет вызовов.** «Брось кубик и получи случайное число» — модель затребовала оба вызова
одним ответом, затем двумя такими же пакетами записала результаты.

**Текст вместе с вызовами.** Поле `content` при вызовах инструментов **необязательно**.
В обычных прогонах эта модель вызывает инструменты молча: событие `assistant_note` не
возникает ни разу. Но если попросить её комментировать действия, она присылает текст и вызов
в одном сообщении — то есть умеет и то, и другое, а молчание есть следствие системного
промпта, где записано «сначала вызовы инструментов, потом ответ».
