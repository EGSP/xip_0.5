# Этап 0.5 — минимальный агентский цикл

Цель этапа одна: получить работающую консольную программу, которая проводит один
агентский цикл, и на ней увидеть своими глазами, как модель запрашивает вызов
инструмента и что происходит дальше. Это не прототип платформы и не заготовка
архитектуры — это учебный стенд, который через несколько дней можно выбросить,
ничего не потеряв.

Всё, что не служит этой цели, из этапа исключено намеренно.

---

## 1. Что должно получиться

Программа запускается в терминале, спрашивает сообщение, обращается к модели,
при необходимости выполняет инструменты и печатает ответ. Каждый шаг виден в
консоли: какой инструмент запрошен, с какими аргументами, что вернул.

Пример работы:

```
> Сколько файлов в каталоге src?

  [шаг 1] модель запросила list_dir({"path":"src"})
  [шаг 1] результат: {"entries":["index.ts","agent.ts", ...]}  (12 имён)
  [шаг 2] модель ответила текстом

В каталоге src 12 файлов.
```

---

## 2. Состав

| Что | Чем |
|---|---|
| Среда | Node 24, TypeScript, ESM (`"type": "module"`) |
| Запуск | `tsx` без предварительной сборки |
| Клиент модели | пакет `openai`, OpenAI-совместимый эндпоинт |
| Режим обращения | обычный запрос, **без потоковой выдачи** |
| Ввод | `node:readline/promises` |
| Хранение | массив в памяти, ничего не персистится |

Один пакет, один `package.json`. Ни Nest, ни Prisma, ни базы данных, ни Effect.

### Почему без Effect

Цель этапа — понять устройство цикла. При одновременном освоении двух незнакомых
предметов непонятно, что именно не работает. Когда цикл заработает, перенос на
Effect занимает около часа и сводится к механическим заменам: `Effect.tryPromise`
вокруг обращения к модели, `Effect.gen` вместо `async` и цикла `for`,
типизированные ошибки вместо `try/catch`. Тогда же станет видно, что Effect
действительно даёт: прерывание хода, таймаут, повторы при отказе модели.

### Почему без потоковой выдачи

В потоковом режиме ответ приходит фрагментами, и аргументы вызова инструмента
собираются из кусков вручную: имя функции приходит в одном фрагменте, аргументы —
по символам в следующих, идентификатор вызова — отдельно. Это самостоятельная
задача, к устройству цикла отношения не имеющая. Обычный запрос возвращает
готовый объект.

## 4. Инструменты

Пять абстрактных инструментов. Первые два недетерминированные: их результат нельзя угадать,
поэтому сразу видно, что модель действительно вызывает инструмент, а не выдумывает ответ.
Остальные три работают с общим состоянием — одним файлом заметок, — и на них проверяется
цепочка зависимых вызовов.

| Имя | Аргументы | Что делает |
|---|---|---|
| `roll_dice` | `count`, `sides` | бросает кубики, возвращает значения и сумму |
| `random_number` | `min`, `max` | случайное целое в диапазоне |
| `read_notes` | нет | читает файл заметок |
| `write_note` | `text` | дописывает строку; **не более трёх строк** |
| `clear_notes` | нет | очищает файл заметок |

Предел в три строки задан намеренно: он заставляет модель столкнуться с отказом инструмента
и показывает, как она его обрабатывает.

Описание инструмента для модели — это имя, текст описания и JSON Schema
аргументов:

```ts
{
    type: 'function',
    function: {
        name: 'list_dir',
        description: 'Возвращает список имён файлов и каталогов по указанному пути',
        parameters: {
            type: 'object',
            properties: { path: { type: 'string', description: 'Путь к каталогу' } },
            required: ['path'],
        },
    },
}
```

Схему на этом этапе пишем руками. Порождение JSON Schema из zod — задача
следующего этапа, здесь она только отвлекает.

Атрибутов инструмента (категория воздействия, источник, признак необратимости)
на этом этапе нет: они нужны для уровней автономии, которых пока тоже нет.

## 5. Цикл

Полная логика этапа умещается в две функции.

```ts
const MAX_ITERATIONS = 10;

async function runTurn(messages: ChatCompletionMessageParam[]): Promise<string> {
    for (let step = 0; step < MAX_ITERATIONS; step++) {
        const response = await client.chat.completions.create({ model, messages, tools: toolSpecs });
        const message = response.choices[0].message;

        // (а) ответ модели добавляется в массив без изменений, вместе с идентификаторами вызовов
        messages.push(message);

        // (б) вызовов нет — модель ответила текстом, ход закончен
        if (!message.tool_calls?.length) {
            return message.content ?? '';
        }

        // (в) вызовы есть — выполняем каждый и добавляем результат
        for (const call of message.tool_calls) {
            const content = await executeTool(call);
            // (г) tool_call_id обязателен и должен совпадать с идентификатором из ответа модели
            messages.push({ role: 'tool', tool_call_id: call.id, content });
        }
    }
    throw new Error(`Превышен предел в ${MAX_ITERATIONS} шагов`);
}

async function executeTool(call: ChatCompletionMessageToolCall): Promise<string> {
    const tool = tools[call.function.name];
    if (!tool) {
        return JSON.stringify({ error: `Инструмент "${call.function.name}" не существует` });
    }
    try {
        const args = JSON.parse(call.function.arguments);
        return JSON.stringify(await tool.execute(args));
    } catch (error) {
        // Ошибка инструмента — штатная ситуация: она возвращается модели, чтобы та исправилась
        return JSON.stringify({ error: error instanceof Error ? error.message : String(error) });
    }
}
```

Ключевой факт, из которого всё следует: **API модели не имеет памяти**. Каждое
обращение отправляет полный массив сообщений заново, и состояние диалога держит
наша программа. Модель ничего не выполняет — она только называет имя функции и
аргументы.

## 6. Журнал событий

Параллельно с массивом сообщений ведём второй массив — перечень того, что
фактически произошло:

```ts
type SessionEvent =
    | { seq: number; at: Date; type: 'user_message';      text: string }
    | { seq: number; at: Date; type: 'tool_call';         callId: string; name: string; args: unknown }
    | { seq: number; at: Date; type: 'tool_result';       callId: string; result: unknown }
    | { seq: number; at: Date; type: 'assistant_message'; text: string };
```

На этом этапе это просто массив, который печатается в консоль. Никакой
подсистемы. Смысл раннего введения только в том, чтобы не сложилась привычка
считать массив сообщений единственным хранилищем: как только появится сжатие
контекста, массив сообщений перестанет соответствовать тому, что произошло, и
разделять их придётся всё равно. Подробнее — в
`Исследования архитектуры/Журнал событий/Зачем нужен журнал событий.md`.

## 7. Чего на этапе не делаем

- потоковой выдачи;
- прерывания хода;
- сжатия контекста и чекпоинтов;
- хранения в базе;
- пользователей, аутентификации, владения объектами;
- уровней автономии и атрибутов инструментов;
- наборов данных, артефактов, памяти, навыков, субагентов;
- MCP;
- сервера, HTTP, SSE.

## 8. Места, где обычно возникают ошибки

1. **Ответ модели с `tool_calls` добавляется в массив как есть**, вместе с
   идентификаторами вызовов. Если добавить только текст или пересобрать объект,
   следующий запрос будет отвергнут.
2. **На каждый вызов нужно ровно одно сообщение с ролью `tool`** и совпадающим
   `tool_call_id`. Пропущенный результат — ошибка API, а не молчаливое
   игнорирование.
3. **Модель может запросить несколько инструментов за один шаг.** Обрабатывать
   нужно все, а не первый.
4. **Аргументы приходят строкой JSON**, которую надо разобрать. Модель иногда
   порождает синтаксически некорректный JSON или значения, не соответствующие
   схеме. Это штатная ситуация: возвращайте текст ошибки результатом вызова,
   модель исправится на следующем шаге.
5. **Ошибка инструмента не прерывает цикл.** Она возвращается модели как
   результат. Прерывать цикл нужно только на дефектах самой программы.
6. **Ограничение числа шагов обязательно с самого начала.** Без него ошибка в
   описании инструмента приводит к тому, что модель вызывает его бесконечно.
7. **Провайдеры OpenAI-совместимого API различаются**: часть возвращает только
   один вызов за шаг, часть иначе обрабатывает пустое поле `content` в сообщении
   с вызовами. Проверяйте на том провайдере, который будете использовать.

---

## 9. Признак того, что этап пройден

Три проверки:

1. Задан вопрос, на который модель отвечает **без** вызова инструментов, — ответ
   получен за один запрос.
2. Задан вопрос, требующий **одного** вызова, — в консоли видны запрос
   инструмента, его результат и итоговый ответ.
3. Задан вопрос, требующий **двух последовательных** вызовов, где второй зависит
   от результата первого (например, «прочитай package.json в том каталоге, где
   лежит index.ts»), — виден рост массива сообщений от запроса к запросу.

После третьей проверки устройство цикла перестаёт быть неочевидным, и можно
переходить к следующему этапу.
